변경마다 **무엇을 바꿨나 / 왜 바꿨나 / 어떻게 검증했나 / 커밋**을 같은 순서로 적습니다.

## 0. Phase 0 기반 정리

AI 에이전트가 안전하게 코드를 고치고, 고친 결과를 스스로 확인할 수 있도록 바탕을 만든 단계입니다. 게임 동작은 거의 바꾸지 않았습니다.

### 0-1. 소스 인코딩을 UTF-8로 통일

- **무엇을 바꿨나**
  - CP949(EUC-KR)로 저장된 소스 20개를 BOM이 붙은 UTF-8로 변환했습니다.
  - 모든 빌드 구성(Debug/Release × Win32/x64)에 컴파일 옵션 `/utf-8`을 추가했습니다.
- **왜 바꿨나**
  - AI 편집 도구는 파일을 UTF-8로 읽고 씁니다. CP949 파일을 그대로 편집하면 한글 주석이 깨집니다.
  - MSVC는 BOM이 없는 파일을 시스템 코드페이지(CP949)로 읽습니다. 원래 ASCII였던 파일에 한글 주석이 추가되면 컴파일러가 잘못 읽게 됩니다. `/utf-8`을 켜면 모든 소스를 UTF-8로 읽습니다.
- **어떻게 검증했나**
  - 변환한 파일을 다시 CP949로 되돌렸을 때 원본과 바이트 단위로 같은지 20개 모두 확인했습니다(무손실).
  - 실제로 바뀐 줄은 한글 주석 98줄과 프로젝트 옵션 4줄뿐입니다.
  - 한글이 든 일반 문자열 리터럴(`"..."`)이 없어서, 실행 동작이 바뀌지 않는다는 것도 확인했습니다.
- **커밋**: `d7c24fb`

### 0-2. 빌드 환경 맞추기 (커밋 없음)

- **무엇을 바꿨나**: 프로젝트 파일은 그대로 두고, 빌드할 때 명령줄에서만 `PlatformToolset=v145`를 지정합니다.
- **왜 바꿨나**: 프로젝트는 VS2022 툴셋(v143)을 기준으로 하는데, 작업 PC에는 VS 2026(버전 18, 툴셋 v145)만 설치돼 있습니다. 프로젝트 파일의 툴셋을 바꿀지는 원작자가 정할 일이라 건드리지 않았습니다.
- **어떻게 검증했나**: 원본 코드가 v145로 경고만 있고 오류 없이 빌드되는 것을 확인했습니다.

### 0-3. 자동 실행 검증: smoke 모드

- **무엇을 바꿨나**: `Client.exe --smoke [폴더]`로 실행하면 다음처럼 동작합니다.
  - 창을 숨기고 소리를 끈 채 Title → Stage1 → Stage2 → Boss를 차례로 실행합니다.
  - 씬마다 마지막 화면을 이미지로 저장합니다.
  - 크래시 없이 끝나면 종료 코드 0을 돌려줍니다.
  - 크래시나 assert가 발생하면 대화상자에서 멈추지 않고 실패 코드로 바로 끝납니다.
- **왜 바꿨나**
  - AI 에이전트는 키보드로 게임을 해볼 수 없습니다.
  - 빌드가 통과해도 씬에 들어가는 순간 크래시가 날 수 있습니다.
  - 그래서 "실행해도 죽지 않는다"를 명령 한 번으로 확인하는 장치가 필요했습니다.
  - smoke test는 "전원을 넣고 연기가 나는지 본다"는 뜻으로, 최소한의 생존 확인을 가리킵니다.
- **어떻게 검증했나**: 4개 씬을 모두 통과(종료 코드 0)했고, 저장된 스크린샷 4장으로 배경, 타일, 캐릭터, 보스가 그려지는 것을 확인했습니다.
- **커밋**: `c681839`

### 0-4. 타이틀 화면에서 시작, 툴 창은 툴 씬에서만 표시

- **무엇을 바꿨나**
  - 시작 씬을 Tool에서 Title로 바꿨습니다.
  - Title에서 T키를 누르면 타일 툴로 갑니다. 툴에서는 원래대로 N키로 타이틀에 돌아옵니다.
  - 타일 아틀라스 창은 툴 씬에 있을 때만 보입니다.
- **왜 바꿨나**
  - 게임을 실행했을 때 개발용 툴이 아니라 게임 화면이 먼저 나와야 합니다.
  - 아틀라스 창 문제는 Notion 할 일 목록의 보류 항목("작은 윈도우 tool scene에서만 출력하게 변경")입니다.
- **어떻게 검증했나**: smoke 모드에서 Title로 시작하는 것을 확인했습니다. 툴 진입 키 동작은 사람이 직접 확인해야 합니다.
- **커밋**: `c681839`

### 0-5. 버그 수정: 마우스가 창 밖에 있으면 타일이 사라짐

- **무엇을 바꿨나**: 타일 생성 함수(`TilePalatte::CreateTile`)에 있던 "마우스가 창 안에 있는가" 검사를, 툴 씬의 클릭 처리로 옮겼습니다.
- **왜 바꿨나**
  - 이 검사는 툴에서 창 밖 클릭을 무시하려고 넣은 것입니다.
  - 그런데 스테이지에 들어갈 때 타일을 불러오는 코드도 같은 함수를 씁니다. 그래서 씬 전환 순간에 커서가 창 밖에 있으면 그 스테이지의 타일이 전부 빠졌습니다.
  - 평소에는 커서가 대부분 창 안에 있어서 눈에 띄지 않았을 것입니다. [추론]
  - 자동 검증에서는 커서 위치가 정해져 있지 않아서, 고치지 않으면 결과가 매번 달라집니다.
- **어떻게 검증했나**: 시나리오 실행 중에는 마우스 좌표가 (0,0)이라 원래 코드라면 타일이 모두 빠집니다. 이 상태에서 Stage1 타일 423개가 모두 로드되는 것을 `count.tile` 값으로 확인했습니다(`Scenarios/stage1_land.txt`).
- **커밋**: `c681839`

## 1. 테스트 하네스

### 1-1. 입력 대본 재생 테스트(`--scenario`) 추가

- **무엇을 바꿨나**: `Client.exe --scenario <대본> <출력 폴더>`를 추가했습니다.
  - 대본에 적힌 키 입력을 프레임 단위로 재생합니다. 예: "60~150프레임 동안 → 누르기", "180프레임에 C(점프)".
  - 프레임마다 플레이어 위치·속도·상태, 레이어별 오브젝트 수를 `state.jsonl`에 기록합니다.
  - `expect`(특정 프레임 검사)와 `always`(매 프레임 검사)로 기대값을 확인하고, 하나라도 어긋나면 실패 코드로 끝납니다.
  - 지정한 프레임의 화면을 저장합니다.
- **용어 설명**
  - **고정 프레임 시간(fixed timestep)**: 실제 경과 시간 대신 매 프레임을 1/60초로 계산합니다. 같은 입력이면 항상 같은 결과가 나오고(결정적 재현), 실제 시간보다 빠르게 돌릴 수 있습니다.
  - **특성 테스트(characterization test)**: "올바른 동작"이 아니라 "지금의 동작"을 기록해 두는 테스트입니다. 물리처럼 감각에 영향을 주는 코드를 고치기 전에 기준선을 잡는 용도입니다.
- **왜 바꿨나**
  - smoke 모드는 "안 죽는다"까지만 확인합니다. 점프가 착지하는지, 대시가 앞으로 가는지는 확인하지 못합니다.
  - 화면을 보고 실시간으로 조작하는 AI 방식은 실시간 액션 게임에 맞지 않습니다. 조사 결과는 다음과 같습니다.
    - VideoGameBench에서 최고 모델도 실시간 모드 진행률이 0.48%였습니다.
    - 소형 게임 연구에서 플랫포머 성공률은 0.64~0.66으로 사람(0.87)보다 낮았습니다. 주된 실패 원인은 AI 응답 지연에 따른 타이밍 실패였습니다.
  - 업계에서는 게임 내부 상태를 읽고 입력을 재생하는 방식이 쓰입니다. 같은 원리를 이 엔진에 맞게 직접 만들었습니다.
- **어떻게 검증했나**: 현재 동작을 기준으로 시나리오 3개를 만들었고 모두 통과합니다.

  | 시나리오 | 확인하는 것 |
  |---|---|
  | `stage1_land` | Stage1에서 떨어져 지면에 착지, 타일 423개 로드 |
  | `stage2_move_jump_dash` | 걷기 → 점프 → 공중 대시 → 착지 → 공격 |
  | `boss_idle` | 보스 패턴 진행(8방향 탄), 오브젝트 수 안정 |

  하네스가 처음 실행되자마자 원본의 결함 두 개를 숫자로 재현했습니다.
  - 낙하 속도가 상한 1000을 넘어 최대 1440까지 올라갑니다.
  - 착지 순간 한 프레임 동안 지면(1726) 아래 1734까지 파고듭니다.

  두 결함은 Phase 1에서 고칩니다.
- **기록된 원본 동작 (기준선)**: 60FPS 고정 조건에서 `state.jsonl`로 측정한 값입니다.

  | 항목 | 값 |
  |---|---|
  | 걷기 | 91프레임에 296.67px (약 196px/초) |
  | 점프 최고 높이 | 220px |
  | 공중 대시 거리 | 233.34px |
  | Stage1 시작 후 착지 | 107프레임 (약 1.8초) |

- **커밋**: `be80ac5`. 사용법은 [Scenarios/README.md](../../Scenarios/README.md)에 있습니다.

### 2-1. 물리·시간·충돌 (E1)

- **무엇을 바꿨나**
  - Rigidbody: 계산만 하던 속도 제한을 실제로 적용했습니다. 떨어지는 속도만 1000으로 제한하고, 점프로 올라가는 속도는 그대로 둡니다. 마찰은 수평 속도에만 걸어서 2023-08 임시 수정을 대체했습니다.
  - Time:
    - 한 프레임 시간을 최대 1/30초로 제한합니다.
    - 시간 배율(`SetTimeScale`)을 추가했습니다. 히트스톱이나 슬로모션에 씁니다.
    - 실제 플레이를 60FPS로 제한합니다.
  - 컴포넌트 갱신 순서: 콜라이더를 마지막에 갱신해서, 이번 프레임에 옮긴 위치로 충돌을 검사합니다.
  - 충돌: Pause·Death 상태 오브젝트는 충돌하지 않습니다. 충돌 중에 비활성이 되면 Exit 콜백을 한 번만 보냅니다.
  - 레이어 반복: 업데이트 도중 오브젝트가 생겨도 안전하도록, 반복 시작 시점의 개수만큼 인덱스로 돕니다.
- **왜 바꿨나**
  - 원본에서 측정된 결함 두 개가 있었습니다. 낙하 속도가 1440까지 올라갔고, 착지 순간 지면 아래로 8px 파고들었습니다.
  - 원본은 FPS 제한이 없어서 PC 성능에 따라 프레임 시간이 달랐습니다. 이 엔진은 프레임마다 속도를 누적해 위치를 계산하므로, 프레임 시간이 다르면 점프 높이도 조금씩 달라집니다. 60FPS로 맞추면 실제 플레이와 자동 검증이 같은 조건에서 돕니다.
  - 스컬 교대로 멈춘(Pause) 머리가 계속 몬스터를 때리고 있었습니다. 수정 전 시나리오에서 268프레임에 몬스터 1마리가 죽었습니다.
- **어떻게 검증했나**: 원본 대비 궤적 비교입니다(60FPS 기준).

  | 항목 | 원본 | 수정 후 |
  |---|---|---|
  | Stage1 최대 낙하 속도 | 1440 | 1000 |
  | Stage1 착지 순간 최저 위치 (지면 1726) | 1734 | 1726 |
  | Stage1 착지 프레임 | 107 | 113 |
  | 점프 최고 높이 / 공중 대시 / 걷기 | 220 / 233.3 / 296.7px | 같음 |

  - 새 시나리오 3개(`e1_fall_speed`, `e1_skull_swap`, `e1_skull_swap_platform`)는 원본에서 실패하고 수정 후 통과합니다.
  - 플레이어가 느낄 수 있는 차이가 두 가지 있습니다. Stage1 첫 낙하가 약 0.1초 길어집니다. FPS 제한이 없던 원본에서는 점프가 약 225px였는데, 이제 220px입니다.
- **커밋**: `02c1be6`, `1cc6412`, `ce1b25b`, `8de71b2`, `41b610f` (머지 `c889c5b`)

### 2-2. 애니메이션·리소스·카메라 (E2)

- **무엇을 바꿨나**
  - 폴더 애니메이션의 프레임을 숫자 순서(자연 정렬)로 읽습니다.
  - 이미지를 파일명이 아니라 전체 경로로 캐시합니다.
  - 없는 애니메이션을 재생하면 크래시하지 않고 디버그 로그만 남깁니다.
  - 반복하지 않는 애니메이션의 완료 이벤트를 끝나는 순간 한 번만 부릅니다.
  - 카메라에 경계 설정(`SetBounds`), 흔들림(`Shake`), 페이드 인·아웃을 추가했습니다.
  - 이미지의 GDI 핸들(DC, 비트맵)을 해제합니다.
- **왜 바꿨나**
  - 프레임 파일명이 `_0`~`_19`처럼 0으로 채워져 있지 않아서, 폴더 순서대로 읽으면 0, 1, 10~19, 2~9 순서로 재생됐습니다. 보스 8방향 탄의 Impact, Loop, Outro 세 애니메이션이 뒤섞여 있었습니다.
  - Resources 폴더에 이름이 같은 파일이 약 198개 있어서, 파일명 캐시는 다른 그림을 가져올 위험이 있었습니다.
  - 원본에서는 완료 이벤트가 애니메이션이 끝난 뒤 매 프레임 불렸습니다. 보스 손의 PutOn 완료 이벤트가 15초 동안 626번 불렸고, 수정 후에는 2번입니다.
  - 카메라 페이드는 코드는 있었지만 켜는 함수가 없어 쓸 수 없었습니다. 우측 경계(3350)도 코드에 고정돼 있었습니다.
  - 이미지를 지울 때 GDI 핸들을 해제하지 않아 누수가 있었습니다. 해제 후 남는 GDI 객체가 333개에서 30개로 줄었습니다.

## 3. Phase 2 게임플레이·렌더링

### 3-1. 게임 로직을 1/60초 고정 단계로 진행

- **무엇을 바꿨나**
  - 게임 로직은 항상 1/60초 단위로 진행하고, 화면은 그 결과를 한 번만 그립니다.
  - 화면이 30FPS로 그려지면 로직은 2번 돌고, 최대 5번까지 따라잡습니다.
  - 디버그 오버레이는 실제 FPS를 표시합니다.
- **왜 바꿨나**
  - 플레이테스트에서 원작자가 "FPS가 30으로 나온다"고 보고했습니다.
  - 측정해 보니 Debug 빌드의 한 프레임 비용이 Stage1 30.2ms, Stage2 19.2ms, Boss 39.5ms였습니다.
  - Phase 1에서 넣은 "한 프레임 최대 1/30초" 상한 때문에, 30FPS보다 느린 보스 씬에서는 **게임이 실제 속도의 약 83%로 느리게 돌고 있었습니다**. 오버레이도 이 상한이 걸린 값으로 계산해서 항상 30을 보여줬습니다.
  - Phase 1의 시간 테스트는 고정 시간으로만 돌아서 이 상황을 잡지 못했습니다.
  - 고정 단계 방식(fixed timestep)은 화면 속도와 게임 속도를 분리합니다. 그래서 느린 PC에서도 물리 결과가 자동 검증과 똑같습니다.
- **어떻게 검증했나**
  - 자동 검증은 한 번 그릴 때 한 단계만 도는 경로라 기존 시나리오가 모두 그대로 통과합니다.
  - 실제 플레이 경로(여러 단계 누적)는 자동 테스트로 확인할 수 없습니다. 원작자가 직접 플레이해서 확인합니다. [미확인]
- **커밋**: `1862051`

### 3-2. 원작 조사와 Phase 2 공통 계약

- **무엇을 바꿨나**
  - 원작 1장의 동작을 조사해 [04. 원작 참고 자료](04-original-reference.md)로 정리했습니다. 조사 범위는 조작, HP, HUD, 적, 보스 패턴입니다.
  - 여러 에이전트가 함께 쓰는 계약 코드를 먼저 만들었습니다.
    - `PlayerStats`: 플레이어 HP. 적·보스는 이것으로만 피해를 줍니다.
    - `Scenario::Publish`: 보스 HP 같은 값을 테스트에 내보냅니다.
    - 시나리오 `damage` 명령: 적 없이도 피격, 체력바, 사망을 테스트합니다.

  - 조사 결과 클론과 원작의 차이가 구체적으로 드러났습니다. 예를 들어 원작은 피격 후 무적이 없습니다. 머리는 8초 자동 복귀가 아니라 쿨다운 6초에 직접 회수하는 방식이고, 대시는 2회이며 대시 중에는 무적입니다.

| 발판 위에서 ↓(하단 점프)가 안 되는 구간 | 대본에 `teleport` 명령을 추가해 Stage2·보스방 발판 전체를 15~20px 간격으로 훑음(서서, 걸으면서, 머리 없는 상태) | 167곳 모두 정상. 재현되지 않음 | 회귀 시나리오 `int_platform_drop` 추가 (`0f01bdc`). 원작자에게 좌표 제보 요청 |
| 타일 툴의 아틀라스 창이 사라짐 | 모니터 정보 확인, 배치 계산을 시나리오 변수로 내보냄 | 창이 화면 x=1600에 고정돼 있어 작업 영역 폭 1440px인 화면 밖에 놓임. 1024px 아틀라스가 화면 높이(852px)보다 큼 | 메인 창의 소유 창으로 바꾸고, 모니터 안쪽에 배치하고, 화면에 맞게 축소. 선택한 타일에 테두리 표시 (`aea5f7e`) |
| 타일 툴에서 우클릭으로 안 지워짐 | 대본에 `mouse` 명령을 추가해 클릭을 재현 | 버튼을 누르고 있는 프레임마다 같은 칸에 타일이 쌓였고, 칸 목록에는 첫 장만 남아 나머지가 지워지지 않음 | 누른 순간과 칸을 옮길 때만 칠하고, 같은 칸은 덮어씀 (`aea5f7e`) |

## 5. 타격감

원작자가 제안 9개 중 7개를 골랐고, Sonnet 에이전트 1명이 구현했습니다(`5eaf6f6`). 수치는 모두 `yaHitFeedback.h`의 `HitFx`에 모아 두어 손맛에 맞춰 바꾸기 쉽습니다.

| 기법 | 값 | 이유 |
|---|---|---|
| 히트스톱 | 일반 0.06초, 2타째·처치 0.10초, 플레이어 피격 0.08초 | 맞는 순간 멈칫해서 타격에 무게가 생김 |
| 하얀 번쩍임 | 0.08초 (DX11 셰이더. GDI 대체 렌더러는 미지원) | 맞았다는 사실이 화면에서 분명히 보임 |
| 적중 소리 | 쓰지 않던 `Skul_Hit 1~3`을 번갈아 재생 | 휘두르는 소리와 맞는 소리를 구분 |
| 화면 흔들림 | 일반 2.5px/0.06초, 강 5px/0.12초 | 타격의 세기를 전달 |
| 엔트 넉백·경직 | 일반 60px·0.4초, 강 110px·0.55초 | 이전(약 18px)에는 맞아도 거의 움직이지 않았음 |
| 공격 전진 | 1타 35px, 2타 55px (낭떠러지 앞에서는 멈춤) | 공격에 체중이 실림 |
| 처치 슬로모션 | 0.4초 동안 0.3배속 (방의 마지막 엔트, 보스 페이즈 전환, 보스 처치) | 마무리 순간 강조 |

**검증**
- 새 시나리오 3개(`g5_*`)로 확인했습니다. 적중하면 시간이 4프레임 멈췄다 다시 흐르고, 번쩍임이 켜졌다 꺼지고, 마지막 엔트를 처치하면 슬로모션이 걸리고, 맞으면 히트스톱이 걸립니다.
- 히트스톱 때문에 타이밍이 밀리는 기존 시나리오 7개에는 시간 연출을 끄는 `timefx off`를 붙였습니다. 기대값은 그대로 두었습니다.
- 넉백이 세져서 연타가 닿지 않게 된 2개에는 `fxknock off`를 붙였습니다.
- 시나리오 36개가 모두 통과합니다.
- 손맛(수치가 적절한지)과 소리는 원작자의 플레이테스트로 확인합니다.
