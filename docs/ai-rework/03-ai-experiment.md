# 03. AI 개발 실험 기록

AI 에이전트로 게임 개발을 하면 어디까지 되는지 확인하는 실험 기록입니다.
누가 무엇을 했는지, 어디서 막혔고 어떻게 풀었는지, 비용이 얼마나 들었는지를 시간 순서대로 남깁니다.
코드 변경 자체는 [02. 단계별 변경 기록](02-changes.md)에 있습니다.

## 실험 설정

| 항목 | 내용 |
|---|---|
| 도구 | Claude Code (모델: Claude Opus 5.5), Windows 11, Visual Studio 2026 Insiders |
| 사람의 역할 | 목표와 범위 결정, 갈림길에서 선택, 직접 플레이해서 손맛 판단 |
| 오케스트레이터 | 메인 AI 세션. 계획을 세우고, 기반 작업을 직접 구현하고, 결과를 검증하고, 머지합니다 |
| 서브에이전트 | 분석이나 구현을 맡아 병렬로 실행되는 AI. 결과는 오케스트레이터에게 보고합니다 |

운영 원칙은 다음과 같습니다.

- 에이전트마다 수정할 수 있는 파일을 나눠서 서로 충돌하지 않게 합니다.
- 에이전트마다 별도 작업 폴더(git worktree)를 씁니다. worktree는 같은 저장소에서 브랜치마다 작업 폴더를 따로 만드는 git 기능입니다.
- 모든 변경은 검증 게이트(빌드 → smoke → 시나리오)를 통과해야 합니다.
- 지시서 첫 단계에서 "기준 커밋이 맞는지 확인하고, 아니면 멈춘다"를 지키게 합니다.

## 문제와 대응

실험에서 생긴 문제를 그대로 남깁니다. AI 개발의 한계와 필요한 안전장치를 보여주는 기록입니다.

| 문제 | 원인 | 대응 | 교훈 |
|---|---|---|---|
| 빌드 도중 컴파일러(`cl.exe`)가 사라짐 | 작업 중에 Visual Studio Installer가 백그라운드로 업데이트됨 | 업데이트가 끝나기를 기다린 뒤 다시 빌드 | 개발 환경이 바뀌면 AI 작업이 멈출 수 있습니다. 코드 문제와 환경 문제를 먼저 구분해야 합니다 |
| 프로젝트 파일 줄바꿈이 바뀜 | Git Bash의 `sed -i`가 CRLF를 LF로 바꿈 | 줄바꿈을 복원하고 원본과 바이트 비교 | 에이전트 지시서에 "프로젝트 파일에 `sed -i` 금지" 규칙 추가 |
| 컴파일 오류 | `std::ifstream file(std::filesystem::path(path));`를 컴파일러가 함수 선언으로 해석(most vexing parse) | 중괄호 초기화로 수정 | 빌드 게이트가 바로 잡아냄 |
| 경고 수가 0으로 나옴 | 증분 빌드라 다시 컴파일된 파일만 셈 | 검증 스크립트가 항상 전체 리빌드하도록 변경(약 2분) | 측정 기준이 흔들리면 비교가 무의미해짐 |
| 첫 시나리오 실패 | 착지 순간 지면 아래로 파고드는 실제 결함 | 기준선은 현재 동작에 맞추고, 엄격한 기준은 Phase 1 목표로 넘김 | 하네스가 첫 실행에 실제 결함을 찾음 |
| 서브에이전트 3명이 모두 작업 전에 멈춤 | 자동 worktree 기능이 현재 브랜치(`AI`)가 아니라 `master`에서 분기함 | 오케스트레이터가 `AI`에서 worktree를 직접 만들어 다시 배정 | 지시서 첫 단계의 "기준 커밋 확인" 규칙이 오래된 코드 위에서 작업하는 사고를 막음 |
| smoke 실행에 실제 키 입력이 섞임 | 오케스트레이터가 만든 smoke 모드가 창을 숨겨도 실제 키보드를 읽음 | E3가 스크린샷 이상(Stage1 자리에 Boss 화면)을 보고 원인을 찾아 수정 | **서브에이전트가 오케스트레이터의 실수를 잡음.** 스크린샷 검증이 숫자 검사로 놓친 문제를 찾음 |
| VS에서 직접 빌드하면 `MSB8020` | 프로젝트는 v143을 지정했는데 이 PC에는 v145만 있음. 자동 검증은 명령줄에서 툴셋을 덮어써서 드러나지 않음 | 기본 툴셋을 자동으로 고르게 변경, 검증 스크립트의 덮어쓰기 제거 | **사람이 발견한 문제.** 자동 검증 환경과 사람의 사용 환경이 다르면 같은 문제를 못 봄 |
| x86 빌드에서 `shellapi.h` 오류 | 오케스트레이터가 `<windows.h>`보다 먼저 include함. unity 빌드라 Debug x64에서는 가려짐 | include 순서 수정 | 한 가지 빌드 구성만 검증하면 다른 구성의 결함을 놓침 |
| 보스 씬이 느리게 돌고 FPS가 30으로 고정 표시 | Phase 1의 "프레임 최대 1/30초" 상한이 느린 Debug 빌드(25~33FPS)에서 게임 시간을 늦춤 | 고정 단계 루프로 교체, 실제 FPS 표시 | **사람의 플레이테스트로 발견.** 고정 시간으로만 도는 자동 테스트는 "느린 PC" 조건을 재현하지 못함 |
| 원작 조사 없이 진행 | 오케스트레이터가 기존 코드와 리소스만 기준으로 삼음 | 조사 에이전트로 원작 기준 문서 작성 | **사람이 방향 오류를 지적.** "모작"이라는 목표의 기준이 원작이라는 점을 AI가 스스로 챙기지 못함 |
| 따로는 통과, 합치면 실패 | 에이전트마다 다른 시점의 코드에서 검증함. 엔트가 공격하고 지면이 바뀌면서 서로의 시나리오 전제가 깨짐 | 머지할 때마다 전체 검증하고, 실패는 작성자에게 되돌려 보냄 | 병렬 개발에서는 **통합 검증이 별도 단계로 꼭 필요함** |
| 멈춤처럼 보인 시나리오 | 느린 GDI(프레임당 40~50ms)에서 다른 빌드와 CPU를 나눠 120초 제한을 넘김 | 제한을 늘림. DX11로 바뀐 뒤 해소 | 실패를 버그로 단정하기 전에 측정 환경부터 확인해야 함 |
| 공용 검증 스크립트를 실행 중에 수정 | 에이전트가 스크립트를 돌리는 동안 오케스트레이터가 내용을 바꿈 → 문법 오류 | 에이전트가 사본으로 다시 실행 | 에이전트가 실행 중일 때는 공용 도구를 수정하지 않음 |
| 사용량 한도 도달 | 에이전트 5명이 동시에 Opus로 실행됨 | 한도가 풀린 뒤 메시지로 이어서 진행. 작업 손실 없음 | 동시 실행 수와 모델 선택이 비용·한도에 직접 영향을 줌 → 토큰 정책 |

### 토큰 절약 정책

모델 단가는 100만 토큰당 입력/출력 기준으로 Opus 5.5 $4/$20, Sonnet 5.5 $2/$10, Haiku 5.5 $0.10/$0.50입니다.

| 작업 | 모델 | 사고 깊이 |
|---|---|---|
| 설계가 어려운 구현 (렌더러 교체 등) | Opus | medium |
| 명세가 분명한 구현, 버그 수정, UI, 흐름 (기본값) | Sonnet | medium |
| 독립 코드 리뷰 | Sonnet | high |
| 기계적 작업 (목록, 검색 요약, 실행 후 요약) | Haiku | low |

그 밖의 원칙은 다음과 같습니다.
- 후속 수정은 이미 맥락을 가진 에이전트에게 메시지로 맡깁니다.
- 작은 수정은 오케스트레이터가 직접 합니다.
- 보고서 길이를 제한하고, 스크린샷은 필요한 것만 봅니다.

- Phase 1의 토큰은 1차 시도(작업 전 중단, 에이전트당 약 5.5만)를 포함한 누적값입니다.
- 시간은 2차 시도 기준이고, 세 에이전트가 동시에 실행됐습니다. 그래서 Phase 1 구현에 실제로 걸린 시간은 가장 오래 걸린 E2 기준 약 45분입니다.

오케스트레이터(메인 세션)의 토큰 사용량은 따로 측정하지 않았습니다. [미확인]

## 지금까지의 관찰

- **AI가 잘한 것**
  - 1만 줄 규모 코드베이스를 몇 분 안에 분석했습니다.
  - 결함을 줄 번호와 함께 찾아냈습니다.
  - 테스트 장치를 만들어 결함을 숫자로 재현했습니다.
  - 지시서의 안전 규칙(기준 커밋이 다르면 멈춤)을 세 에이전트가 모두 지켰고, 원인과 해결책까지 정확히 보고했습니다.
- **AI만으로 안 되는 것**
  - 실시간 액션 게임을 직접 플레이할 수 없습니다. 그래서 입력 대본 재생이라는 우회로를 만들었습니다.
  - 손맛, 판정 타이밍, 밸런스는 판단할 수 없습니다. 사람의 플레이테스트가 필요합니다.
  - 설치 업데이트, 권한 설정 같은 개발 환경 문제는 사람이 확인하거나 기다려야 합니다.
- **병렬 구현에서 확인한 것 (Phase 1)**
  - 수정할 파일을 미리 나눠 주니 머지 충돌이 한 건도 없었습니다.
  - 세 에이전트 모두 "실패하는 시나리오 먼저 → 수정 → 통과" 순서를 지켰습니다. 궤적 표, 스크린샷 비교 같은 근거도 함께 보고했습니다.
  - 맡은 범위 밖의 버그를 찾으면 직접 고치지 않고 후속 과제로 보고했습니다(순간이동 후 공중에 뜸, 사운드 키 충돌 등). 소유권 규칙이 지켜졌습니다.
  - 지시받은 범위 안에서 판단도 했습니다. E1은 낙하 속도만 제한하고 상승 속도는 두었습니다. 대칭으로 제한하면 점프 높이가 바뀌기 때문이라는 이유도 남겼습니다.
  - 오케스트레이터의 결함을 서브에이전트가 찾았고, 오케스트레이터와 서브에이전트가 모두 못 본 문제(`MSB8020`)는 사람이 찾았습니다. 검증하는 쪽이 여럿일수록 서로의 빈틈을 메웁니다.
- **아직 확인하지 못한 것**: 실제 창을 띄운 플레이에서의 조작감. 에이전트는 BGM 때문에 창 모드를 실행하지 않았고, 손맛은 판단할 수 없습니다. 사람의 플레이테스트로 확인합니다.
